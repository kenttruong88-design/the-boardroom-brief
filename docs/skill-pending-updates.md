# Skill pending updates (for human review)

- Fresh `/tmp` scratch clones have no git identity configured (no global `~/.gitconfig` on the device VM) — first `git commit` fails with "Author identity unknown". Fix: `git config user.email "kentt@theboardroombrief.local"` and `git config user.name "Kent"` (read from the mounted repo's local config, which does have it set) before committing in the scratch clone.
- `/tmp` on the device VM accumulates files from unrelated prior runs owned by `nobody:nogroup` (not the current session's uid); reusing a common scratch filename (e.g. `/tmp/verify_final.py`) hits "Permission denied" on write. Fix: give scratch scripts written to `/tmp` on the device VM a unique/session-specific name, don't assume a generic name is free.
- Fork-type subagents dispatched for Layer-2 research in this session had `WebSearch` but no `WebFetch`/page-fetch tool at all, not just the usual Quora/InterNations gating — every "real voice" had to be paraphrased from search-result titles/secondary reporting rather than fetched thread text. All forks disclosed this honestly via `sources.note`; no quotes were fabricated. Worth checking whether fork subagents reliably get WebFetch in this environment, since it's a bigger gap than the Quora/InterNations-specific one already documented.
- `references/genimg-template.py` has a hardcoded date literal baked into the Cloudinary `public_id` (`f"2026-11-07-{ARTICLE_NUM}-{SLUG}-{label}"`), left over from whichever run last edited it — it silently mis-tags every image's public_id with a stale date on any run that isn't that exact day. Fix: worked around this run with `sed -i 's/2026-11-07/<today>/' ` on the local copy before invoking it; the template itself should take the date as an argv parameter instead of a literal, so this doesn't need re-patching by hand every single run.
- Writing a Python script via heredoc and then immediately `python3`-running it in the SAME `device_bash` call can return stale/incorrect results (observed: a dedup check against the real archive wrongly reported 0 hits for a known-duplicate pair like `philippines-vs-hong-kong`); re-running the identical script file in a separate, subsequent `device_bash` call gave correct results. Root cause unclear (possibly FS sync latency in the device bridge). Fix: always split "write script" and "run script" into two separate `device_bash` calls.
